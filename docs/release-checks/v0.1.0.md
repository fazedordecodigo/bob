## Fluxo

- E0: `check` e os quatro `verify` passaram (4.907 testes em cada runner), e `publish` foi pulado. O artefato `release-assets` contém exatamente `SHA256SUMS`, `bob_quality-0.1.0-py3-none-any.whl` e `install.sh`. `sha256sum -c SHA256SUMS` retornou `OK` para o wheel e o instalador (Linux x64).
- E1: `check`, os quatro `verify` (4.907 testes em cada runner) e `publish` passaram. [v0.1.0](https://github.com/fazedordecodigo/bob/releases/tag/v0.1.0) retornou `isPrerelease=true` e os mesmos três nomes de assets; a tag aponta para o commit acima. Os dois assets baixados da pré-release passaram no `sha256sum -c SHA256SUMS`, e o manifesto publicado bate com o artefato de E1.
- Comparação antecipada para E6: os assets dos dois runs passam seus checksums, mas o `SHA256SUMS` de E1 difere do de E0. O hash do wheel em E0 é `00ad2fefd7c7c51b0dcc59ded34b668a839f6ec34861b1eba143f9adc58d2e5c`; em E1 é `02ee53befa852f36551f5f54fc61c46f8c77d82905a77d44e1451eb0c40b69b8`. Os 86 arquivos dentro do wheel têm conteúdo idêntico, mas os timestamps ZIP são diferentes. O `install.sh` é idêntico byte a byte.
- Em 2026-11-26, Emerson aprovou manter a `v0.1.0` e usar o `SHA256SUMS` de E1 como referência de E6. O build do wheel não é reproduzível byte a byte: só os timestamps do ZIP diferem entre E0 e E1. Como a promoção não faz rebuild, E6 confere que os assets publicados em E1 continuam inalterados.
- E2 antes de promover (`releases/latest`): HTTP `404` com `gh api`; o `curl` anônimo retornou HTTP `403` com `x-ratelimit-remaining: 0`, inclusive após aguardar o horário de reset informado pela API.
- E3: a linha de instalação pública com `BOB_VERSION=v0.1.0` em um projeto Git novo (Linux x64, Node 22.18.0) saiu `0` com `bob doctor: 0`. `bob --version` retornou `bob 0.1.0` e `project skills: 0.1.0 (.agents/skills)`.
- `bob update`: saiu `4` com `could not read the latest release (HTTP 403)` com e sem `BOB_VERSION=v0.1.0`. O comando consulta `releases/latest` mesmo com a variável definida e não seleciona pré-releases; a verificação bem-sucedida no endpoint público fica pendente até haver uma release estável.
- E5: pendente; a pré-release não foi promovida. As checagens alternativas do Cursor não verificam a listagem nativa em E4, que exige autenticação não disponível neste ambiente.
- E6: pendente; a verificação pós-promoção será feita contra o artefato de E1.

## Roteiro da release (E0–E6)

Feito pelo Emerson. Nenhum agente dispara nem publica.

### E0 — Ensaio sem publicar

```bash
gh workflow run release.yml --repo fazedordecodigo/bob --ref main -f tag=v0.1.0 -f prerelease=true -f dry_run=true
gh run list --repo fazedordecodigo/bob --workflow release.yml --limit 1
gh run download <run-id> --repo fazedordecodigo/bob --name release-assets --dir /tmp/bob-e0
cd /tmp/bob-e0 && sha256sum -c SHA256SUMS
```

Prova: os jobs `check` e os 4 `verify` verdes, o `publish` pulado; o artefato `release-assets` tem só `install.sh`, `bob_quality-0.1.0-py3-none-any.whl` e `SHA256SUMS`; `sha256sum -c SHA256SUMS` dá OK nos 2 arquivos. No macOS, use `shasum -a 256 -c SHA256SUMS`.

### E1 — Criar a pré-release

```bash
gh workflow run release.yml --repo fazedordecodigo/bob --ref main -f tag=v0.1.0 -f prerelease=true -f dry_run=false
gh release view v0.1.0 --repo fazedordecodigo/bob --json isPrerelease,assets --jq '.isPrerelease, [.assets[].name]'
```

Prova: `true` e os 3 assets `install.sh`, `bob_quality-0.1.0-py3-none-any.whl` e `SHA256SUMS`.

### E2 — A pré-release não é a última release

```bash
curl -s -o /dev/null -w '%{http_code}' https://api.github.com/repos/fazedordecodigo/bob/releases/latest
```

Prova: `404`. A API devolve só a release mais nova que não é pré-release nem rascunho (ADR 0011).

### E3 — Instalar a pré-release num projeto novo

```bash
mkdir /tmp/bob-e3 && cd /tmp/bob-e3 && git init -q
printf 'print(1)\n' > app.py && git add app.py && git commit -qm init
curl -fsSL https://github.com/fazedordecodigo/bob/releases/download/v0.1.0/install.sh | BOB_VERSION=v0.1.0 sh
bob --version
```

Prova: o comando sai `0` com `bob doctor: 0` no resumo, e a 1ª linha do `bob --version` é `bob 0.1.0`.

### E4 — Verificação manual nos 5 agentes e no prompt de IA

No projeto do E3, preencha as tabelas "Verificação manual" e "Prompt de IA" acima (data UTC-3, versão do agente, saída ou captura).

```bash
curl -s https://api.github.com/repos/fazedordecodigo/bob/releases/latest | python3 -c 'import json, sys; print(json.load(sys.stdin)["tag_name"])'
```

### Se E3 ou E4 falhar

- Não promova. A `v0.1.0` fica como pré-release e nenhum Dev a recebe pelo comando único (E2 segue `404`).
- Registre a falha neste arquivo e abra uma issue.
- A correção entra na `main` e sai como pré-release nova com tag nova (`v0.1.1`, com `pyproject.toml` = `0.1.1`). Tags não são reaproveitadas. O fluxo recomeça no E0.
- Apagar a pré-release falhada é decisão do Emerson.
