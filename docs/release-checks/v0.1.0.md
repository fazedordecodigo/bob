# Release check v0.1.0

Registro da release `v0.1.0` (CT13). O workflow `release` publica este arquivo como notas da release. O Emerson preenche as tabelas durante o roteiro abaixo.

- Commit: `<sha>`
- Run do release.yml: `<url>`

## Comando de Verificação na matriz (automático)

O job `verify` do workflow `release` roda em cada plataforma: `shasum -a 256 -c SHA256SUMS` nos assets do run, `cmp` do `install.sh` com `scripts/install.sh`, o `bob doctor`, o `pytest` e o `sh scripts/verify-install.sh` (passos 1 a 14) com o wheel do run (`VERIFY_DIST`).

## Roteiro da release (E0–E6)

Feito pelo Emerson. Nenhum agente dispara nem publica.

### E0 — Ensaio sem publicar

```bash
gh workflow run release.yml --repo fazedordecodigo/bob --ref main -f tag=v0.1.0 -f prerelease=true -f dry_run=true
gh run list --repo fazedordecodigo/bob --workflow release.yml --limit 1
gh run download <run-id> --repo fazedordecodigo/bob --name release-assets --dir /tmp/bob-e0
cd /tmp/bob-e0 && sha256sum -c SHA256SUMS
```

Prova: os jobs `check` e os 4 `verify` verdes, o `publish` pulado; o artefato `release-assets` tem só `install.sh`, `bob_quality-0.1.0-py3-none-any.whl` e `SHA256SUMS`; `sha256sum -c SHA256SUMS` dá OK nos 2 arquivos. No macOS, use `shasum -a 256 -c SHA256SUMS`.

### E1 — Criar a pré-release

```bash
gh workflow run release.yml --repo fazedordecodigo/bob --ref main -f tag=v0.1.0 -f prerelease=true -f dry_run=false
gh release view v0.1.0 --repo fazedordecodigo/bob --json isPrerelease,assets --jq '.isPrerelease, [.assets[].name]'
```

Prova: `true` e os 3 assets `install.sh`, `bob_quality-0.1.0-py3-none-any.whl` e `SHA256SUMS`.

### E2 — A pré-release não é a última release

```bash
curl -s -o /dev/null -w '%{http_code}' https://api.github.com/repos/fazedordecodigo/bob/releases/latest
```

Prova: `404`. A API devolve só a release mais nova que não é pré-release nem rascunho (ADR 0011).

### E3 — Instalar a pré-release num projeto novo

```bash
mkdir /tmp/bob-e3 && cd /tmp/bob-e3 && git init -q
printf 'print(1)\n' > app.py && git add app.py && git commit -qm init
curl -fsSL https://github.com/fazedordecodigo/bob/releases/download/v0.1.0/install.sh | BOB_VERSION=v0.1.0 sh
bob --version
```

Prova: o comando sai `0` com `bob doctor: 0` no resumo, e a 1ª linha do `bob --version` é `bob 0.1.0`.

### E4 — Verificação manual nos 5 agentes e no prompt de IA

No projeto do E3, preencha as tabelas "Verificação manual" e "Prompt de IA" acima (data UTC-3, versão do agente, saída ou captura).

### E5 — Promover sem rebuild

Só se E3 e E4 passam (o Claude Code fica registrado como está, pelo RA1).

```bash
gh release edit v0.1.0 --repo fazedordecodigo/bob --prerelease=false --latest
```

Ou pela interface: editar a release `v0.1.0`, desmarcar "Set as a pre-release", marcar "Set as the latest release" e salvar. A tag não muda e o workflow não roda de novo.

### E6 — Conferir depois de promover

```bash
curl -s https://api.github.com/repos/fazedordecodigo/bob/releases/latest | python3 -c 'import json, sys; print(json.load(sys.stdin)["tag_name"])'
gh release download v0.1.0 --repo fazedordecodigo/bob --dir /tmp/bob-e6
cd /tmp/bob-e6 && sha256sum -c SHA256SUMS && cmp SHA256SUMS /tmp/bob-e0/SHA256SUMS
```

Prova: `v0.1.0`; `sha256sum -c SHA256SUMS` dá OK; o `SHA256SUMS` é igual ao do E0.

### Se E3 ou E4 falhar

- Não promova. A `v0.1.0` fica como pré-release e nenhum Dev a recebe pelo comando único (E2 segue `404`).
- Registre a falha neste arquivo e abra uma issue.
- A correção entra na `main` e sai como pré-release nova com tag nova (`v0.1.1`, com `pyproject.toml` = `0.1.1`). Tags não são reaproveitadas. O fluxo recomeça no E0.
- Apagar a pré-release falhada é decisão do Emerson.
